> 작성 기준: 2026-09-04

## 1. 사례 개요

### 사례 이름

**업무 설명 기반 카탈로그 Agent 설계 Copilot**  
부제: 자연어 업무 설명을 Langflow 구현 청사진과 HTML 업무 개선 보고서로 전환하는 AI Agent

### AI 활용 방식

| 방식 | 적용 | 적용 내용 |
| --- | :---: | --- |
| AI Agent | O | 업무 설명을 분석하고, 카탈로그 후보를 검토해 Agent화 설계안을 생성한다. |
| Skill |  | 별도 Skill 실행이 핵심이 아니라, 카탈로그 기반 설계·검증 Flow가 핵심이다. |
| Plugin |  | 별도 Plugin 의존 없이 Langflow 1.11.0의 standalone custom component로 구성했다. |
| MCP | O | 로컬 MCP로 사내 Agent Hub의 기능 카탈로그를 JSON으로 추출해 Flow 입력으로 사용한다. |
| Prompt | O | 1차 설계 후, 분기·예외·권한·입출력 계약을 강화하는 전용 품질 보완 Prompt를 한 번 더 적용한다. |
| Harness | O | Pydantic structured output, 결정론적 정규화·검증, fallback, 테스트로 LLM 출력을 안전한 보고서 계약으로 제한한다. |
| 기타 | O | 카탈로그 링크를 type/id로 재생성하고, Langflow 1.11 구현용 Input·Output 포트 설계를 보고서에 표시한다. |

### 한 줄 설명

**현업이 업무를 말로 설명하면, 로컬 MCP로 추출한 사내 기능 카탈로그를 근거로 AI가 재사용 가능한 기능을 선별하고, Agent화 방법·입출력 연결·분기·예외까지 담은 HTML 구현 청사진을 만들어 주는 설계 Agent입니다.**

## 2. 해결하려는 업무 문제

### 대상 업무

업무 자동화 또는 Agent 도입을 검토하는 현업 업무 전반입니다. 예를 들어 주간 보고서 취합, 다중 시스템 데이터 조회, 승인 요청 처리, 문서 검토, 알림·게시 업무처럼 사람의 판단과 반복 처리, 여러 시스템 연결이 함께 필요한 업무를 대상으로 합니다.

### 기존 업무 방식

1. 현업 담당자가 자연어·회의·문서로 업무를 설명한다.
2. 설계자와 개발자가 업무 흐름, 예외, 승인 기준, 필요한 데이터와 시스템을 다시 확인한다.
3. 기존 Component·Flow가 있는지 여러 화면과 자료에서 수작업으로 찾는다.
4. 후보 기능의 입출력, 권한, 실제 적용 위치를 정리해 설계 문서를 만든다.
5. 현업과 개발자가 여러 번 문서를 왕복하며 보완한다.

### 주요 불편/병목

- 같은 업무 설명을 현업, 기획, 개발 인력이 반복 해석해 초기 설계 시간이 길어진다.
- 기존 Component·Flow를 찾지 못해 이미 있는 기능을 다시 만들거나, 반대로 관련 없는 기능을 억지로 적용할 위험이 있다.
- 업무의 분기, 오류 처리, 담당자 검토, Input·Output 계약이 문서마다 누락되거나 표현 방식이 달라진다.
- 숙련자가 아니면 “무엇을 Agent로 만들 수 있는지”, “어디에 사람이 개입해야 하는지” 판단하기 어렵다.
- 결과가 회의 메모나 자유형 문서에 머물러 Langflow Canvas 구현으로 바로 이어지기 어렵다.

### 이 업무에 AI가 필요했던 이유

업무 설명을 구조화하고 카탈로그 후보를 비교하는 일은 반복적이지만, 실제 적용 여부는 업무 맥락·예외·보안·기존 자산의 계약을 함께 봐야 합니다. AI는 넓은 후보를 빠르게 검토하고 초안을 만드는 역할을 맡고, 사람은 실제 업무 적합성 및 배포 가능 여부를 최종 판단하도록 역할을 분리했습니다.

## 3. 제작 내용

### 주요 기능 (3개)

1. **MCP 기반 카탈로그 준비 및 100개 후보 검색**
   - 로컬 MCP가 사내 Agent Hub에서 기능 카탈로그를 JSON으로 추출합니다.
   - 사용자는 추출된 JSON 한 개를 Flow에 업로드합니다. Flow 실행 중 MongoDB나 벡터 DB가 필요하지 않습니다.
   - 로컬 키워드·BM25·문자 n-gram 기반 RRF 검색으로 업무 설명과 관련된 상위 100개 후보를 찾습니다.

2. **LLM의 맥락 기반 후보 선별 및 이중 설계**
   - 별도 LLM 노드가 100개 후보 중 실제 설계에 검토할 shortlist를 기본 12개(1~30개 조절 가능)로 선별합니다.
   - shortlist에 든 자산을 반드시 쓰도록 강제하지 않습니다. 업무와 맞지 않으면 미사용으로 남기고, 신규 standalone custom component가 필요하다고 제안할 수 있습니다.
   - 1차 설계 뒤에는 전용 품질 보완 Prompt로 분기, 예외 처리, 사람 검토 지점, 입출력 연결, 보안·운영 고려사항을 한 번 더 다듬습니다.

3. **Langflow 구현 청사진과 HTML 보고서 생성**
   - AS-IS 업무 흐름과 Agent 적용 후 TO-BE 흐름을 시각화합니다.
   - 각 단계의 역할, 추천 카탈로그 자산, 선정 이유, Agent Hub 상세 링크, Langflow 1.11 기준 Input·Output 타입과 이전/다음 연결을 표시합니다.
   - 업무 설명이 부족해도 중단하지 않고 보완이 필요한 항목과 다시 입력할 문장 예시를 보고서에 제시합니다.

### 작동 흐름

```text
사내 Agent Hub
   └─ 로컬 MCP: 기능 카탈로그 JSON 추출
                                │
사용자 업무 설명 + 카탈로그 JSON ─┤
                                ▼
01. JSON 검증·정규화·안전 링크 생성
                                ▼
02. 로컬 다중 신호 검색: 관련 후보 상위 100개
                                ▼
03. LLM 후보 선별: 업무 맥락에 맞는 shortlist 생성
                                ▼
04~07. 1차 업무 분석·Agent 설계 JSON 생성 및 정규화
                                ▼
08~10. 전용 보완 Prompt·최종 설계 검증
                                ▼
11~16. 화면 계약 → 반응형 HTML 보고서 → 선택 게시/결과 안내
```

### 최종 산출물

- 업무 설명 원문과 부족한 정보 목록
- 현재 업무(AS-IS) 흐름: 단계, 분기, 예외, 병목
- Agent 적용 후(TO-BE) 흐름: 자동화 단계, 사람 검토 지점, 오류·재시도 경로
- 카탈로그 기반 적용 계획: 선택·검토·미사용 후보 구분, 선정 이유, 필수 확인 사항, Agent Hub 상세 링크
- Langflow 1.11 구현 청사진: 노드별 Input·Output 이름, 타입(Data/Message 등), 이전/다음 노드 연결 방향
- 신규 기능이 필요할 때의 standalone custom component 요구 명세
- 위험·통제·테스트 체크리스트와 선택적 HTML 보고서 링크

### 사용자 검토/승인 절차

**있음.** 다만 Flow 실행 중 HITL을 강제하지 않습니다. 보고서에 부족한 정보와 보완 문장 예시를 표시하고, 사용자가 업무 설명을 수정해 전체 Flow를 다시 실행하는 방식입니다. 실제 운영 적용 또는 신규 Component 개발 전에는 보고서의 필수 확인 사항을 설계자·보안 담당자가 검토합니다.

## 4. 업무 변화 및 효과

| 구분 | 적용 전 | 적용 후 |
| --- | --- | --- |
| 업무 절차 | 현업 설명을 여러 역할이 재해석하고, 기존 기능 탐색과 설계 문서 작성을 수작업으로 반복 | 업무 설명과 카탈로그 JSON을 한 번 입력하면 후보 검색, LLM 선별, 설계 초안·보완, HTML 보고서까지 단일 Flow로 생성 |
| 소요 시간 | 초기 설계안 작성 시간은 담당자 경험과 자료 탐색 시간에 크게 좌우 | 단일 실행으로 1차 설계안을 생성하고, 보고서의 보완 항목만 반영해 재실행하는 반복 방식으로 축소 |
| 반복 작업 | 카탈로그 목록 탐색, 후보 비교, 링크 정리, 업무 흐름 문서화가 반복 | 후보 100개 검색 → LLM shortlist → 링크·근거·설계안을 자동 정리 |
| 오류/품질 | 누락된 예외·승인 조건·입출력 계약, 관련 없는 기존 기능의 오적용 가능성 | 구조화 출력·정규화·검증으로 형식을 고정하고, shortlist 밖 자산의 임의 적용을 차단하며, 부족한 정보는 보고서에 명시 |

### 가장 크게 개선된 부분

**“업무를 설명하는 단계”와 “Agent를 구현하기 위한 설계를 만드는 단계” 사이의 공백을 줄인 것**입니다. 단순히 업무를 요약하는 것이 아니라, 기존 자산을 어떤 단계에 어떤 이유로 적용할지와 Langflow Canvas에서 필요한 데이터 연결까지 함께 보여 줍니다.

### 정량 효과 또는 체감 효과

- 카탈로그 전체를 사람이 훑는 대신, 로컬 검색으로 **상위 100개 후보**를 만들고 LLM이 **기본 12개 shortlist**로 선별합니다.
- 검색 후보, LLM 선별 후보, 실제 적용 후보를 분리하여 “후보를 찾았으니 반드시 사용한다”는 오류를 줄였습니다.
- 단일 Flow는 **18개 실행 노드, 30개 실행 연결**으로 구성되어 있으며, 사용자 관점에서는 Playground 채팅창 또는 Canvas의 업무 설명과 카탈로그 JSON만 입력하면 됩니다.
- 1차 설계와 품질 보완을 분리해, 사용자가 추가 지시로 “분기와 예외를 더 구체화”, “사람 승인 유지” 같은 요구를 반영할 수 있습니다.
- Langflow 1.11.0 런타임 검증 및 관련 자동 테스트 **81건 통과**로 Flow export, standalone component, 보고서 계약의 회귀를 점검했습니다.

> 운영 도입 후에는 `초기 설계안 도출 시간`, `카탈로그 탐색 시간`, `재검토 횟수`, `구현 전 발견한 계약 누락 건수`, `실제 재사용 자산 비율`을 동일 업무군별로 전·후 측정해 정량 효과를 업데이트합니다.

### 기타 의견

카탈로그는 추천의 근거이지 강제 규칙이 아닙니다. LLM은 후보 안에서만 실제 적용 여부를 판단하며, 불필요한 재사용을 피하고 필요한 경우에는 신규 standalone custom component의 요구 명세를 제안합니다.

## 5. 사용법

### [주의 사항]

1. 업무 설명에는 실제 비밀번호, API Key, 토큰, 개인정보 원문을 입력하지 않습니다.
2. 카탈로그 JSON에는 자산 메타데이터만 넣고 실제 secret 또는 인증값은 포함하지 않습니다.
3. 보고서의 카탈로그 자산이 `metadata_only`이면 실제 적용 전에 해당 Component·Flow의 Input·Output 포트, 권한, 네트워크 제약을 확인해야 합니다.
4. 보고서는 설계·검토 산출물입니다. 실제 운영 배포, 외부 시스템 연결, 권한 부여는 별도 승인 절차를 거칩니다.
5. LLM이 추천한 후보를 무조건 사용하지 않습니다. 업무 적합성·운영 계약·보안 검토를 기준으로 사람이 최종 결정합니다.

### [사용 방법]

1. 로컬 MCP를 실행해 사내 Agent Hub의 기능 카탈로그를 JSON으로 추출합니다.
2. Langflow 1.11.0에서 `F01_business_work_design_single.json`을 import합니다.
3. Playground으로 실행할 때는 `00A Playground 업무 설명 입력`의 채팅창에 업무 목표, 대상 시스템, 현재 절차, 결과물, 예외·승인 기준을 가능한 구체적으로 입력합니다. Canvas에서 직접 실행할 때는 `00 업무 설명 입력`의 업무 설명 원문을 사용하며, Chat 원문이 있으면 Chat 내용이 우선합니다.
4. `01 기능 카탈로그 JSON 파일`에 MCP가 추출한 UTF-8 JSON 파일 한 개를 업로드합니다.
5. `02 관련 기능 카탈로그 검색`의 검색 후보 수를 기본 100으로 두고, `03 LLM 카탈로그 후보 선별`의 최대 후보 수를 업무 복잡도에 맞게 1~30 사이에서 조정합니다.
6. `05 Language Model`에 Structured Output 또는 tool calling을 지원하는 사내 승인 모델을 연결합니다.
7. Run 후 HTML 보고서에서 AS-IS/TO-BE 흐름, 카탈로그 적용 계획, 보완 필요 항목, 노드별 입출력 연결을 확인합니다.
8. 보완 항목이 있으면 업무 설명을 수정하고 같은 Flow를 다시 실행합니다.

### [사용 예시]

```text
매주 금요일, Outlook과 JIRA에서 이번 주 프로젝트별 업무 정보를 취합해
주간 보고 초안을 만들고 싶습니다.

- 메일 제목에 [주간업무]가 포함된 메일과 JIRA 이슈를 수집한다.
- 프로젝트별로 완료 업무, 진행 중 업무, 이슈·리스크, 다음 주 계획으로 분류한다.
- 각 문장에 원본 메일 또는 JIRA 링크를 남긴다.
- 자동 발송 메일과 중복 항목은 제외한다.
- 민감정보와 누락 여부를 담당자가 검토한 뒤에만 사내 포털에 게시한다.
- 인증 만료나 조회 실패 시에는 게시하지 않고 실패 원인과 누락 건수를 알린다.

추가 설계 요청: 기존 카탈로그 자산을 우선 검토하되, 포트 계약이 불명확하면
신규 standalone custom component 요구 명세로 표시해 주세요.

최종 설계 보완 지시: 승인·반려·오류 경로와 각 단계의 Langflow Data/Message
Input·Output 연결을 구체적으로 표시해 주세요.
```

### [API Key 필요 여부 및 발급 가이드 링크]

- **LLM 실행:** 필요. 조직에서 승인한 LLM provider의 credential을 Langflow의 Secret/환경 설정으로 연결합니다. 키를 업무 설명, 카탈로그 JSON, Prompt, 보고서에 직접 입력하지 않습니다.
- **카탈로그 추출 MCP:** 사내 Agent Hub 접근 권한이 있는 로컬 인증 세션을 사용합니다. Flow에 인증 정보를 저장하지 않습니다.
- **보고서 게시 API:** 선택 사항입니다. URL을 비워 두면 self-contained HTML 파일만 생성합니다.
- **가이드 링크:** `[사내 LLM Provider Credential 발급 가이드]`, `[사내 Agent Hub/MCP 접근 권한 가이드]`를 제출 조직의 실제 링크로 교체합니다.

### [추가 의존성]

- Langflow 1.11.0 / langflow-base 0.11.0 / lfx 1.11.0 호환 런타임
- Structured Output 또는 tool calling을 지원하는 조직 승인 Language Model
- 로컬 MCP로 추출한 UTF-8 기능 카탈로그 JSON 한 개
- 선택 사항: 기존 HTML Report API
- MongoDB, embedding DB, Run Flow, 실행 중 Human Input은 이 단일 Flow의 필수 의존성이 아닙니다.

### [기타 참고 사항]

- Custom component는 모두 한 파일 안에서 동작하는 **standalone 형식**으로 설계했습니다. sibling/local import나 Flow 간 Run Flow 호출을 전제로 하지 않습니다.
- 카탈로그 `type`이 `py/component`이면 Agent Hub Component 링크, `json/flow`이면 Flow 링크를 `id` 기반으로 안전하게 생성합니다.
- LLM structured output이 지원되지 않는 경우에도 전체 응답 JSON과 스키마를 다시 검증하며, 2차 보완 단계만 실패하면 검증된 1차 설계로 보고서를 계속 완성합니다.
