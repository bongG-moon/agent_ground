# 사용자 스타일 기반 회의록 작성 Flow

회사에서 녹음 파일을 TXT로 변환한 결과와, 사용자가 과거에 직접 작성한 Word/TXT 회의록을 함께 제공하면 **사용자가 평소 무엇을 남기고 무엇을 생략하는지까지 반영한 회의록**을 작성하는 Langflow `1.9.2` Flow입니다.

과거 회의의 사실을 검색해 현재 문서에 붙이지 않습니다. 과거 녹취와 실제 회의록의 차이에서 작성 스타일만 일반화하고, 현재 회의록의 사람·수치·일정·결정은 현재 녹취에서만 가져옵니다.

## 제공 파일

- 개별 Import: [`meeting_minutes_writer_flow.json`](meeting_minutes_writer_flow.json)
- 연결표: [`CONNECTION_GUIDE.md`](CONNECTION_GUIDE.md)
- 첫 실행 샘플: [`samples/`](samples/)
- 재사용 DRM Component: [`../../components/drm_document_text_extractor/USAGE_GUIDE.md`](../../components/drm_document_text_extractor/USAGE_GUIDE.md)

## 필요한 입력

| 입력 | 개수 | 형식 | 의미 |
| --- | ---: | --- | --- |
| 과거 녹취 | 1~10개 | TXT 권장 | 과거 회의에서 실제로 말한 전체 내용 |
| 과거 실제 회의록 | 과거 녹취와 동일 | TXT, DOCX, DOC 등 | 사용자가 실제로 정리해 둔 결과 |
| 현재 녹취 | 정확히 1개 | TXT | 지금 회의록으로 만들 내용 |
| 추가 작성 지시 | 0~1개 | Chat Input | 포함할 주제, 제외할 내용, 특별한 강조 기준 |
| 회의 제목·일자·참석자 | 선택 | Builder 입력 | 녹취에 없거나 문서 머리말에 고정할 정보 |

### 과거 파일 짝짓기

두 목록은 **업로드 순서로 1:1 대응**합니다.

```text
과거 녹취 1번  ↔  실제 회의록 1번
과거 녹취 2번  ↔  실제 회의록 2번
과거 녹취 3번  ↔  실제 회의록 3번
```

파일 수가 다르면 스타일 비교가 왜곡되므로 Flow가 명확히 실패합니다. 파일명은 같지 않아도 되지만 같은 회의를 나타내는 파일을 같은 순서에 놓아야 합니다.

과거 녹취와 과거 회의록은 각각 하나의 다중 파일 입력칸에 1~10개를 동시에 넣을 수 있습니다. 현재 회의 여러 건을 일괄 처리하는 구조는 아니므로 `현재 녹취`에는 항상 한 파일만 넣습니다.

| 과거 녹취 업로드 순서 | 과거 회의록 업로드 순서 | 처리 결과 |
| ---: | ---: | --- |
| `historical_transcript_01.txt` | `historical_minutes_01.docx` 또는 `.txt` | 첫 번째 스타일 비교 쌍 |
| `historical_transcript_02.txt` | `historical_minutes_02.docx` 또는 `.txt` | 두 번째 스타일 비교 쌍 |
| 세 번째 과거 녹취 | 세 번째 실제 회의록 | 세 번째 스타일 비교 쌍 |

파일명 숫자를 읽어 자동 정렬하는 방식이 아니므로 파일 선택 화면에 표시된 순서를 실행 전에 확인해야 합니다.

## 처리 순서

```text
과거 녹취 TXT 목록 ── DRM 미사용 추출 ─┐
과거 실제 회의록 ── 로컬/DRM 추출 ────┼─> 녹취-회의록 쌍 정리
현재 녹취 TXT 1개 ── DRM 미사용 추출 ──┤
추가 포함·제외 지시 ───────────────────┘
                                      ↓
                    사용자 스타일 분석
           (선택·생략 기준, 섹션, 문장, 액션 형식)
                                      ↓
                    현재 회의록 초안 작성
                                      ↓
               현재 녹취·지시·스타일 최종 검토
                                      ↓
                     최종 회의록 + 검토 보고서
```

하나의 승인된 Language Model을 세 단계에서 순서대로 사용합니다. 스타일 분석은 JSON 프로필을 만들고, 초안 작성은 현재 녹취와 해당 프로필만 사용하며, 최종 검토는 초안을 현재 녹취와 다시 대조합니다.

## Standalone 구현 원칙

이 Flow의 `04 요청 정리`, `05 스타일 분석`, `06 초안 작성`, `07 최종 검토`는 각각 **한 Python 파일만으로 동작하는 Standalone Node**입니다.

- 다른 프로젝트 Python 파일을 `import`하지 않습니다.
- 보조 함수, 프롬프트, 검증 규칙과 비동기 실행 로직을 해당 Node 파일 안에 모두 포함합니다.
- Flow JSON에는 각 Standalone Python 원본 전체를 노드 코드로 내장합니다.
- 개별 파일을 다른 환경으로 옮기거나 Flow JSON을 다시 Import해도 프로젝트 폴더 경로를 요구하지 않습니다.
- 공용 기능으로 재사용할 가치가 있는 DRM 텍스트 추출만 독립 Component로 유지하고, 회의록 중간 payload에 종속된 네 단계는 Flow 내부 Node로 구분합니다.

## Word 회의록과 DRM

`02 과거 실제 회의록 읽기`는 공용 `drm_document_text_extractor`를 사용합니다.

- 기본값 `자동(로컬 우선)`: 일반 DOCX/TXT는 로컬에서 읽고 실패 파일만 DRM API로 전달
- `항상 DRM API`: 조직 DRM이 로컬 파서에도 일부 내용을 노출할 수 있거나 보호 문서를 확실히 API로 보내야 할 때 사용
- `DRM 미사용`: 비보호 샘플만 로컬에서 시험할 때 사용

DRM API가 필요한 경우에만 API 주소, Secret 토큰과 사번을 Builder에 입력합니다. 이 값은 Flow JSON에 저장하지 않습니다. Component 출력은 복호화된 원본 Word 파일이 아니라 **평문 텍스트**입니다.

## 추가 작성 지시 예시

```text
의사결정과 담당자·기한이 있는 후속 조치 위주로 작성해줘.
인사말, 회의 시작 전 잡담, 같은 내용의 반복 설명은 제외해줘.
품질 지표 변경 사유와 다음 주 검증 계획은 근거까지 자세히 남겨줘.
확정되지 않은 일정은 확정된 것처럼 쓰지 말고 [확인 필요]로 표시해줘.
```

사용자가 직접 입력한 포함·제외 지시는 학습된 스타일보다 우선합니다. 다만 현재 녹취에 없는 사실을 추가하라는 지시는 따르지 않습니다.

## 사용자 스타일로 반영하는 항목

- 문서의 제목과 첫 부분 형식
- 섹션 순서와 제목 표기 방식
- 문단형·글머리표·표 형식의 선호
- 문장 종결과 전반적인 상세 수준
- 발언자 이름을 표시하는 빈도
- 의사결정과 액션아이템 표현 형식
- 녹취에서 회의록에 남기는 내용의 선택 기준
- 인사말·반복·잡담 등 생략 기준

과거 회의의 이름·수치·결정은 스타일 프로필에 남기지 않도록 지시하고, 문구 예시는 `[담당자]`, `[안건]`, `[기한]` 같은 자리표시자로 일반화합니다.

## 첫 실행

1. [`samples/`](samples/)의 과거 녹취 2개를 `01 과거 녹취 TXT 읽기`에 순서대로 넣습니다.
2. 대응하는 과거 회의록 2개를 `02 과거 실제 회의록 읽기`에 같은 순서로 넣습니다. 실제 Word 입력을 시험하려면 `.docx` 두 개를 선택합니다.
3. `current_transcript.txt`를 `03 현재 녹취 TXT 읽기`에 단독으로 넣습니다.
4. Word 보호 문서를 사용한다면 `02`의 DRM 주소·토큰·사번을 입력합니다.
5. `추가 작성 지시` Chat Input에 포함·제외 기준을 작성합니다.
6. `회의록 작성·검토 Language Model`에 긴 한국어 문맥과 JSON 출력을 지원하는 조직 승인 모델을 선택합니다.
7. `08 최종 회의록 출력`까지 실행합니다.

제공 샘플은 실제 장문 회의를 흉내 내도록 구성했습니다.

- `historical_transcript_01.txt`: 220개 발언의 고객 문의 자동 분류 개선 회의
- `historical_transcript_02.txt`: 220개 발언의 영업 예측 대시보드 데이터 품질 회의
- `historical_minutes_01.docx`, `historical_minutes_02.docx`: Builder에 바로 넣을 수 있는 실제 Word 회의록 예시
- `historical_minutes_01.txt`, `historical_minutes_02.txt`: Word 예시와 내용이 같은 원문·확인용 TXT
- `current_transcript.txt`: 220개 발언의 자동 회의록 운영 시범 전환 회의
- `ADDITIONAL_INSTRUCTIONS.md`: 현재 회의에서 강조·제외할 내용의 입력 예시
- `EXPECTED_RESULT.md`: 모델 출력에서 확인할 사실과 스타일 기준

두 과거 회의는 서로 다른 주제를 다루지만 회의록은 같은 작성 습관을 유지합니다. 따라서 모델은 과거 업무 사실을 복사하는 대신 안건별 통합, 확정·미확정 분리, 표 기반 후속 조치, 잡담 생략 같은 반복 스타일을 찾을 수 있습니다.

같은 번호의 `.docx`와 `.txt`를 동시에 넣으면 동일 회의가 두 번 학습되므로 둘 중 한 형식만 선택합니다. 일반 Word 파일은 `자동(로컬 우선)` 모드에서 로컬 추출되며, 실제 사내 DRM 보호 Word 파일은 로컬 추출 실패 시 설정된 DRM API로 전달됩니다.

## 출력

- `최종 회의록: Message`: 사용자의 기존 스타일을 반영한 Markdown 회의록 본문만 반환합니다. `final_minutes`, `corrections`, `remaining_checks`를 감싼 JSON은 기본 Chat Output에 표시하지 않습니다.
- `회의록 검토 보고서: Data(JSON)`: 초안·최종 길이, 스타일 신뢰도, 수정 유형, 사람이 확인할 항목

`08 최종 회의록 출력`에는 첫 번째 Message 출력만 연결되어 있어 아래처럼 제목부터 바로 복사해 사용할 수 있습니다.

```markdown
# 자동 회의록 운영 시범 전환 의사결정 회의

- 일시: 2026-06-17
- 참석: 서팀장, 문과장, 조책임, 임대리, 송매니저

## 의사결정
...
```

담당자·조치·기한 표는 각 행이 별도 줄인 유효한 Markdown 표로 출력됩니다. 모델이 아래처럼 행 줄바꿈을 빼고 한 줄로 반환하더라도 최신 `06 초안 작성`과 `07 최종 검토` Node가 표 구조를 복구합니다.

```text
후속 조치 | 담당 | 조치 | 기한 | | --- | --- | --- | | 담당자A | 조치 내용 | 2026-06-22 |
```

복구된 기본 출력은 다음 구조입니다.

```markdown
## 후속 조치

| 담당 | 조치 | 기한 |
| --- | --- | --- |
| 담당자A | 조치 내용 | 2026-06-22 |
```

수정 내역과 확인 필요 목록이 필요한 경우에만 두 번째 `회의록 검토 보고서` 출력을 별도 JSON/Data 출력 Node에 연결합니다. 검토 보고서에는 녹취 원문이나 DRM Secret을 넣지 않습니다.

## 실패와 제한

- `05 사용자 회의록 스타일 분석`에서 `name 'analyze_meeting_minutes_style' is not defined`가 발생하면 이전 JSON을 Import한 상태입니다. 최신 `meeting_minutes_writer_flow.json`을 다시 Import해야 합니다.
- 원인은 Langflow Custom Component 로더가 최상위 `async def`를 실행 범위에서 제외할 수 있기 때문이며, 현재 버전은 각 Standalone 파일 안의 일반 함수가 내부 코루틴을 생성하는 방식으로 수정했습니다.
- 최종 화면에 `{"final_minutes": ...}` 전체가 보이면 검토 모델의 JSON 객체 응답을 이전 Node가 본문으로 처리한 상태입니다. 최신 JSON은 문자열·객체·중첩 객체·이중 인코딩 응답에서 `final_minutes`만 분리하고, 분리할 수 없는 JSON은 원문 그대로 노출하지 않고 오류로 중단합니다.
- `후속 조치 | 담당 | ...`가 한 줄 텍스트로 보이면 이전 JSON을 Import한 상태입니다. 최신 JSON은 한 줄로 붙은 Markdown 표의 헤더·구분선·데이터 행을 다시 나누므로 Flow를 다시 Import해야 합니다.
- 과거 녹취와 실제 회의록의 개수가 다르면 실행하지 않습니다.
- 현재 녹취는 정확히 한 개만 허용합니다.
- 예시가 너무 길면 파일당·전체 문자 제한에 맞게 자르고 경고합니다.
- 모델이 스타일 JSON을 만들지 못하면 잘못된 스타일로 진행하지 않고 실패합니다.
- 모델 Context Window가 과거 예시와 현재 녹취의 전체 길이보다 작으면 예시 수 또는 문자 제한을 줄여야 합니다.
- 검토 모델이 있어도 사실 정확성을 완전히 보장할 수 없으므로 대외 공유·승인 전에는 사람이 원문과 최종 회의록을 확인해야 합니다.

현재 상태는 `user_testing`입니다. Langflow 1.9.2 template과 Graph 계약, 가짜 모델 기반 회귀 테스트를 통과한 뒤에도 실제 사내 DRM 문서와 승인 모델을 연결한 사용자 확인 전에는 `approved`로 변경하지 않습니다.
